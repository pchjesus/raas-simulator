## 0. 적용 원칙·우선순위·판정 용어

이 문서는 범용 v1.1을 **교육 시뮬레이터 맥락에 맞춰 적용**한 전문 표준이다. 범용 디자인의 일반적 경향이 시뮬레이터의 정확성·학습 흐름·장비 재현·상태 계약을 압도하지 않는다.

- **MUST (필수):** 학습 명료성, 과학적·임상적 정직성, 접근성, 사용자 데이터 보호, 기존 승인 계약 및 핵심 상태와 관련된 규칙. 충돌·예외는 이유와 권한을 기록하고 필요한 승인을 받는다.
- **SHOULD (권장):** 대체로 유용한 레이아웃·표현·프로세스·사용성 패턴. 합리적인 근거와 검증 계획이 있으면 조정할 수 있다.
- **MAY (선택):** 개별 시뮬레이터에 맞는 표현·토큰·구현 예시. 예시를 기존 값의 강제 교체 지시로 해석하지 않는다.
- **참고 ≠ 복제:** Braun 기기, ChatGPT, Apple HIG 등은 해결 원리만 분석한다. 제품 사진·고유 그래픽·상표·전체 레이아웃을 무단 복제하지 않는다.
- **권한 우선순위:** 법률·의료/과학적 안전 요구와 프로젝트의 최신 명시적 승인 계약 → 프로젝트별 상태·데이터·UX 정책 → 승인된 본 전문 지침 → 범용 지침의 권장 패턴. 실제 충돌은 **임의로 통합하지 말고** 사용자에게 선택지와 위험을 보고한다.
- **원본 보존:** 기존 v1.0은 승인된 기록이므로 별도로 보존한다. v1.1 채택 시 원본을 제거하거나 소급 변경하지 않는다.
- **현황 재확인:** 아래 10장의 버전·경로·기능은 **v1.0 작성 당시 계약의 보존 기록**이다. 실제 변경 전에 `main` 최신 소스, `AGENTS.md`, `SPEC.md`, `README.md`, `DEVLOG.md`, 승인 PR/설계·상태 전환 계약을 확인한다. 최신 버전인 것처럼 추정하지 않는다.
- **검증 수준:** 설계 검토, 정적 검사, 자동 테스트, 브라우저/실기기 테스트, 사용자 사용성 조사, 임상/전문가 검토는 별개다. 실행하지 않은 검증을 통과(PASS)로 표시하지 않는다.

**핵심 목표:** 학습자가 별도의 사용법 학습에 시간을 소모하지 않고 **왜 여기 있는지 → 무엇을 관찰·조작할지 → 무엇이 달라졌는지 → 그 변화가 무엇을 의미하는지**를 이해하도록 돕는다.

## 1. 교육 목적과 사용자 여정

### 1.1 학습 목적과 대상 사용자

- **MUST:** 변경 범위마다 대상 학습자(초심자/숙련자), 선행지식, 학습 목표 **1개 이상**, 관찰·판단할 핵심 현상, 수행 과제, 성공 여부를 확인할 방법을 정한다.
- **MUST:** 처음 방문한 학습자가 화면의 용도와 **명확한 시작 행동**을 파악할 수 있어야 한다. 숙련자가 기존 시뮬레이터로 바로 들어가는 **자유 탐색 경로**도 유지한다.
- **SHOULD:** 기본 여정은 **목적 제시 → 관찰/탐색 → 예상·통제된 조작 → 즉시 피드백 → 해석·복습**으로 구성한다. 다만 같은 순간에 관찰해야 하는 파형·경로·수치를 단계별 화면으로 억지 분리하지 않는다.
- **MUST:** 처음 배우는 개념과 이미 익힌 조작을 구분한다. 툴 사용법을 익히느라 학습 목표를 놓치지 않도록, 필수 설명은 관련 조작 근처에 제공한다.
- **SHOULD:** 진행 단계·현재 주제·남은 활동·재진입 위치를 알기 쉽게 표현한다. 실제 저장을 하지 않았다면 '이어하기 가능'으로 오해하게 하지 않는다.

### 1.2 핵심 내부 설계 레퍼런스

**Boyacto PB980 학습실 (Ventilator Simulator)**: commit [`5be92ce`](https://github.com/pchjesus/ventilator-simulator/commit/5be92ce76469eca0309b2b6daf225fcfc05a1b1d), `learn.html`, `learning-room.css`, `src/learning-room.js`, `docs/LEARNING_ROOM.md`.

이 학습실의 **A 도입 → B 장비 탐색 → C 단일 과제 실습**은 **학습 정보 구조의 참고 사례**다. 세 프로젝트에 동일한 탭이나 파일 구성을 강제하는 규칙이 아니며, 기존 원본 장비 화면은 기능·사용성 비교 및 회귀 검증을 위해 유지한다.

## 2. 디자인 철학과 레퍼런스 활용

### 2.1 Dieter Rams / Braun: 'Less, but better'를 교육 시뮬레이터에 적용

람스의 10원칙은 공식 문구의 직역이 아니라 이 프로젝트를 위한 **디지털 설계 해석**으로 적용한다.

| 원칙 | 시뮬레이터에서의 판단 기준 |
|---|---|
| 혁신적 | 학습자가 개념을 더 잘 관찰·조작·해석하는 데 기여할 때만 새 시각화/기술을 도입한다. |
| 유용함 | 보기 좋은 장식보다 학습 목표, 원인-결과 비교, 작업 정확도를 먼저 개선한다. |
| 심미적 | 정렬, 간격, 정보 그룹과 시각적 리듬을 일관되게 설계한다. |
| 이해 가능 | 어떤 제어가 어떤 모델 변수에 영향을 주는지 알 수 있게 한다. |
| 절제 | 도구와 장식이 파형·수치·학습 내용을 압도하지 않게 한다. |
| 정직함 | 실제 측정, 모델 계산, 생성 예시, 고정 화면, 허구 사례를 구분한다. |
| 오래 지속됨 | 재사용 가능한 컴포넌트와 단일 데이터 출처를 유지해 확장·보수하기 쉽게 한다. |
| 세부까지 철저함 | 경계·축·단위·초점·오류·작은 화면·초기화까지 점검한다. |
| 환경 배려 | 불필요한 자동재생, 반복 렌더링, 무거운 에셋을 줄인다. |
| 최소한의 디자인 | 불필요한 강조를 줄이되 핵심 생리학 정보·안전 고지를 숨기지 않는다. |

**실제 제품의 관찰점을 반드시 '문제 → 패턴 → 검증'으로 연결한다.**

| Braun 제품 | 관찰 지점 | 교육 시뮬레이터 적용 가능성 | 오용 방지 |
|---|---|---|---|
| **T3 Pocket Radio (1958)** | 격자·간격·핵심 조작의 비례 | 학습 툴바, 설정 요약 카드, 좁은 화면 정렬 | 장비 화면 전체를 T3처럼 단순화하지 않음 |
| **ET66 Calculator** | 기능별 버튼 그룹·강조색·즉시성 | Accept/Cancel·약물·속도·실습 제어의 역할 구분 | 교육적으로 필요한 장비 제어를 임의로 제거하지 않음 |
| **SK4 (1956; Hans Gugelot 공동 작업)** | 구조가 드러나는 구성·조작부 구분 | 시뮬레이터 본체와 학습 설명 레이어 구분 | 의료기기 외형을 무단 차용하지 않음 |
| **T1000 World Receiver (1963)** | 고밀도 패널·눈금·라벨의 질서 | ECG·혈역학·경로·다수 설정의 동시 관찰 | 밀도 자체를 줄이기 위해 인과관계 단절 금지 |

ET66의 기여를 디터 람스 한 사람에게 단정하지 않고 Dietrich Lubs 등과의 맥락을 확인한다. 실제 작품의 사진·도면·브랜드 자산 사용권은 별도로 검토한다.

### 2.2 보완 레퍼런스의 선택적 활용

- **ChatGPT 인터페이스:** 학습 시작 화면, 장문 설명, 도움말에서 여백과 명확한 주 행동을 참고한다. **시뮬레이터 본체를 채팅 UI로 만들라는 뜻이 아니다.**
- **Apple Human Interface Guidelines:** 탐색·취소·뒤로 가기·피드백·상태 전환·필요한 모션을 참고한다. Apple 전용 API와 외관을 웹에 강제하지 않는다.
- **KRDS:** 한국어 입력·라벨·오류·상태 전달·접근 가능한 폼의 참고. 디자인 패턴 도입만으로 로그인·서버 저장·파일 업로드가 구현되지는 않는다.
- **NHS Design System:** 건강 안내·안전 고지·용어와 양식의 명료성.
- **IBM Carbon:** 디자인 토큰·색의 의미·복합 데이터·표/그래프.
- **WCAG 2.2:** 해당 범위의 접근성 검사 기준.

**MUST:** 레퍼런스를 인용할 때는 이름보다 **해결하려는 학습·사용성 문제, 가져올 패턴, 채택하지 않을 부분**을 기록한다. 서로 충돌하는 패턴을 아무 설명 없이 혼합하지 않는다.

### 2.3 표현적 정체성과 장비 충실도의 균형

- **MUST:** 디자인을 정돈한다는 이유로 장비의 의도된 재현도, 생리학 인과관계, 학습 피드백, 시나리오 경계를 지우지 않는다.
- **SHOULD:** 도입·학습실·안내에서는 프로젝트의 교육적 정체성과 매력적인 시각 표현을 사용할 수 있다. 그러나 **장비 UI와 학습용 UI는 역할상 구분**하며, 시각적 효과가 학습 근거인 것처럼 보이게 만들지 않는다.
- **MUST:** 기존에 승인된 컬러·레이아웃·엔진 표현 방식은 이 문서의 예시 팔레트나 Braun 레퍼런스를 근거로 **무단 교체하지 않는다**.

## 3. 교육용 시뮬레이터 핵심 원칙 (MUST)

1. **목적 우선:** 새 학습자가 의도와 시작 행동을 이해하며, 기존 이용자의 자유 탐색 경로도 열린다.
2. **핵심 행동의 초점:** 작업별 주 행동은 분명하되, 같은 순간에 비교해야 하는 자료는 동시에 보여준다.
3. **단계적 정보 공개, 정보 손실 금지:** 보조 설명은 접거나 분리해도 중요한 경고·시간·조건·모델 한계·현 단계 풀이에 필요한 값은 감추지 않는다.
4. **정보 위계:** 제목 → 짧은 맥락 → 핵심 시각화/내용 → 주 행동 → 부차적 설명 순서를 상황에 맞게 적용한다. 중복 헤더·카드 중첩·서로 경쟁하는 CTA를 억제한다.
5. **역할이 명확한 시각 언어:** 중립적 읽기 표면과 상태 중심 강조를 우선하되 브랜드 표현도 허용한다. 색만으로 상태를 말하지 않는다. Boyacto 청색 `#2854cc`, 장비 어두운 색 `#10232c`, 연습 녹색 `#15745c`는 **참고값이며 강제값이 아니다**.
6. **과학·임상 데이터의 정직성:** 관찰·실측·모델 계산·교육용 생성·고정 표시·허구 사례를 구분한다. 화면의 정교함이 임상 검증·정확한 예측을 의미하지 않는다.
7. **모델과 UI 상태의 분리:** 탭·렌더·도움말·학습실 이동이 계산 상태를 몰래 초기화·탐색·자동재생·변경하거나 정답을 누설하면 안 된다. 엔진은 단일 진실 공급원(single source of truth)이어야 한다.
8. **접근성 우선:** 키보드 조작, 초점 표시·복귀, 의미적 레이블, 상태 피드백, 예측 가능한 반응형 배치와 움직임 감소를 처음부터 고려한다.
9. **학습 효과는 검증 과제:** 스크린샷이나 코드 통과만으로 학습 효과를 주장하지 않는다. 초심자 과제 성공, 오류, 재탐색, 설명 가능성, 인지적 부담을 별도로 평가한다.
10. **기존 데이터·세션 보호:** 업데이트 시 기존 학습 답안·설정·진행 상태·저장 구조를 보존한다. 영속 저장을 새로 도입하는 것은 기존 RAM 세션의 자동 보존과 같지 않으며 별도 정책/승인이 필요하다.
11. **조작의 피드백과 복구:** 적용·취소·재시도·초기화·오류·이용 불가를 구분하고, 실행되지 않은 결과나 저장 완료를 암시하지 않는다.
12. **검증의 정직성:** 테스트 범위·실행 환경·증거 수준·미검증 사항을 명시한다. 교육적 효과, 임상적 안전성, 실기기 사용성은 각각 검증해야 한다.

## 4. 시각 언어 및 정보 표현의 기본값

이 절의 숫자는 **권장 시작점**이며 기존 프로젝트의 승인된 디자인·기기 제약을 소급 변경하지 않는다.

### 4.1 레이아웃·타이포그래피·밀도

- **SHOULD:** 본문은 약 **16px 이상**, 부가 학습 설명은 가급적 **14px 이상**, 장문 설명 행간은 약 **1.5~1.7**부터 검토한다. 작은 도식 라벨은 확대·살펴보기·인접 큰글씨 정보처럼 **동등한 판독 경로**를 제공한다.
- **SHOULD:** 한국어·영어 의학용어·수치·기호 혼합 화면은 `ch` 단위의 가상 폭만 믿지 않는다. 실제 용어·단위·첨자·긴 약물 이름·표·인용·링크를 320/360/390px에서도 시험한다.

## 8. 버전 호환성·학습 상태·저장/복원 계약

**'상태 보존'은 단순히 새로고침 후 화면이 같은 모양으로 보인다는 뜻이 아니다.** 기존 시뮬레이터에서 의도적으로 **일시적(RAM)**인 상태와 **영속 저장** 상태를 구분해야 한다.

### 8.1 데이터·상태의 범주

| 종류 | 예시 | 보존/전환 판단 원칙 |
|---|---|---|
| 실행 중 시뮬레이션 상태 | 타이머·위상·현재 변수·파형 진행 | 기존 엔진의 일시정지/재시작/복귀 계약 준수. 새로고침 보존을 임의로 약속하지 않음 |
| 학습 상태 | 단계·완료 여부·퀴즈 답안·피드백 | 기존 탭·세션 전환 계약과 정답 공개 정책 유지 |
| 임상/CASE 상태 | 가상 환자·시나리오·QA 제한·사례 답안 | 해당 프로젝트의 공개·안전·모델 분리 규칙 유지 |
| 확정 설정·로컬 사용자 데이터 | 저장된 설정, 승인된 진행 기록(있는 경우) | 기존 저장 방식·스키마·보존 정책 확인 후 호환성 검증 |
| 표현용 UI 상태 | 열린 패널, 초점, 필터, 임시 입력 | 저장 여부와 무관하게 재진입·취소·복귀 동작을 명확히 정의 |

### 8.2 구버전 호환성 및 마이그레이션

- **MUST:** 저장 키·스키마·URL·상태 구조·탭 계약을 바꿀 때 **구버전 읽기 호환 / 명시적 마이그레이션 / 사용자가 이해할 수 있는 이전 방식** 중 적절한 경로와 실패·롤백 전략을 정한다.
- **MUST:** 실제 이전 버전 구조를 대표하는 익명/가상 픽스처를 사용해 **이전 → 새로고침 → 재진입 → 재설정·복구 → 필요 시 이전 버전 롤백**을 테스트한다. 개인정보·환자 데이터는 테스트 저장소와 로그에 포함하지 않는다.
- **MUST:** 새로 만든 저장 기능이 **기존 RAM 세션 또는 엔진 시간까지 자동 보존**한다고 가정하지 않는다. 저장 범위/복원 시점/버전 충돌을 문서화하고, 제품의 승인 없이는 새 영속 저장 계약을 도입하지 않는다.
- **MUST:** 이전 데이터가 실제 삭제되지 않아도 새 UI에서 접근할 수 없으면 **호환성 실패**로 기록한다. 실패·부분 이전·중복·손상·용량 초과 시 사용자에게 정확한 상태와 복구 대안을 안내한다.
- **SHOULD:** 데이터 맵에 `(이전 버전/키/스키마) → (새 버전/키/스키마)`, 이전 규칙, 복구 방식, 테스트 근거를 남긴다. 기존 저장이 없다면 **N/A**로 적는다.

### 8.3 프로젝트별 주의

- **Ventilator:** 원래 `learn.html`과 `index.html`을 오갈 때 RAM 세션 유지가 보장된다는 가정 금지. 영속 상태 연계 시 기존 승인 필요.
- **RAAS:** 시뮬레이션 단계·약물 효과·학습 답안·임상 학습 진도를 복제·혼합하지 않는다. 원본 크기 그래프의 접근성을 유지한다.
- **Cardiac:** 전환 시 `physiological/visualization` 시간, 타임라인, Play/Pause, 탭 학습 답안 등은 **기존 v1.13 전환 계약**을 우선 적용한다. 영속 저장을 새로 추가하라는 의미가 아니다.

## 9. 검증 계약·보고·학습 효과 평가

### 9.1 변경 전에 작성할 검증 계약

최소한 **①요구/불변조건 ②작업 시나리오 ③기대 결과 ④실행 환경/검사 방법 ⑤증거 ⑥상태**를 기록한다. 검증 항목과 범위는 7.2의 위험도와 영향 분석에 맞춰 선택한다.

| 검증 구분 | 관찰·기록 예시 | 주장 가능한 범위 |

### 11.3 원본의 유지·제외 사항

- 원본 v1.0의 **APPROVED future-design guideline** 상태는 소급 변경하지 않는다. 새 v1.1은 사용자 요청에 따른 적합성 검토 후 **APPROVED future-design guideline (2026-10-15)**으로 채택한다. 제품별 구현·배포·설계 변경은 별도 승인 및 검증 대상이다.
- 개인적인 Pinterest/Awwwards/Behance 무드보드 수집은 **개발 선행조건, 승인 게이트, 납품 항목이 아니다**. 개별 레퍼런스 도입은 사용자가 구체적으로 선택한 때만 고려한다.
- 문서·슬라이드 전용 규칙과 블로그 DOI 작성 규칙처럼 시뮬레이터 목적에 직접 필요하지 않은 일반 조항은 범용 지침에 남기고 여기서는 **교육용 화면·과학 모델·학습 검증**만 전문화했다.

## 12. 검토 체크리스트 (요구사항/실행 결과 분리)

### 학습 경험
- [ ] 초심자의 목적·시작 행동과 숙련자의 자유탐색 경로가 명확한가?
- [ ] 관찰 → 조작 → 원인 설명 → 복습 흐름이 학습 목표를 지지하는가?
- [ ] 시각적 단순화를 위해 인과적으로 연결된 파형·변수·경고를 분리/숨기지 않았는가?

### 과학·임상 정직성
- [ ] 실제/모델/교육용 생성/고정 예시/허구 시나리오를 적절히 구분했는가?
- [ ] 단위·축·기준·시간·모델 제한·임상적 비검증 고지가 유지되는가?
- [ ] 임상 CASE 공개와 QA 전용의 경계가 기존 계약대로 유지되는가?

### 기능·상태 보존
- [ ] 기존 단일 엔진과 Play/Pause/Seek·약물·설정·답안 전환 계약이 유지되는가?
- [ ] Pending/Committed/Cancel, 탭 복귀, 초기화, 포커스 복귀가 정의되어 있는가?
- [ ] 저장하지 않기로 한 RAM 상태를 저장한다고 약속하거나 자동 영속화하지 않았는가?
- [ ] 구조 변경 시 구버전 픽스처·재진입·실패·마이그레이션·롤백을 시험했는가(해당 없으면 N/A)?

### 시각·접근성
- [ ] 과제 특성에 맞는 정보 밀도와 장비 재현도/학습용 UI 분리가 유지되는가?
- [ ] 한국어 의학용어·영문·첨자·단위·그래프 라벨이 충분히 읽히는가?
- [ ] 320/360/390px, 태블릿/데스크톱, 텍스트 200% 확대와 320px 상당 리플로우를 별도로 확인했는가?
- [ ] 키보드·포커스·움직임 감소·대비·색 외 상태 설명을 검토했는가?

### 구현·검증·승인
- [ ] `main` 및 프로젝트 승인 문서를 확인하고 변경 위험도(L/M/H)를 기록했는가?
- [ ] 기존 기능과 데이터에 대한 영향 분석·되돌릴 방법을 마련했는가?
- [ ] 각 검증 항목을 PASS / FAIL / NOT RUN / N/A로 분리하고 환경·증거를 남겼는가?
- [ ] 사용자 사용성·임상 전문 검토·실기기 검증의 수행 여부를 정확히 구분했는가?
- [ ] 사용자 승인이 필요한 설계 변경이 실제로 승인되었는가?
